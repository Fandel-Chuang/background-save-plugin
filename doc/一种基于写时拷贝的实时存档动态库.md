# 一种基于写时拷贝的实时存档动态库

在使用 C++ 开发游戏/业务服务器时，“不停服热更”几乎是所有团队都会面对的难题。传统方案很多，但都伴随权衡与隐患。本文提出并落地了另一种工程化思路：基于写时拷贝（Copy-On-Write, CoW）的“实时存档”动态库，通过在热更前生成一致性快照，实现状态持久化与平滑切换，兼顾低侵入与高可靠。

本文所述实现基于开源项目 Background Save Plugin（Redis RDB 风格持久化），支持跨平台，面向 C/C++ 服务端工程可直接集成。项目地址（GitHub）：https://github.com/Fandel-Chuang/background-save-plugin.git

---

## 背景与问题

典型 C++ 服务器的热更难点主要在于：
- 线程多、内存状态复杂，状态分布在对象图中，难以“整体冻结/迁移”
- ABI 兼容性脆弱，动态库热更易因二进制布局差异导致未定义行为
- 热更窗口需尽可能短，避免影响业务

工程实践中常见的几类方案：

### 1) 服务无状态化
- 1.1 使用 Redis 存状态
  - 优点：天然支持扩缩容、可靠性强、生态完善
  - 缺点：
    - 网络 hop 带来延迟与抖动，对高实时性逻辑不友好
    - 状态模式受限于 KV 结构；复杂对象需序列化与拆装
    - 强一致回放复杂，尤其涉及事务/多 key 事务性
- 1.2 共享内存存储玩家状态
  - 优点：进程间共享，切换快
  - 缺点：
    - 需要自定义内存管理器、版本与 schema 演进成本极高
    - 崩溃恢复、数据校验与回滚难
    - 复杂对象（指针/引用）跨进程不可移植
- 1.3 逻辑插件化（逻辑在动态库中）
  - 优点：看似“换 dll/so 就热更”
  - 缺点：
    - ABI 不稳定（虚函数表、布局变化）极易触发崩溃
    - 状态仍在进程内存，迁移成本不低
    - 回滚难且不透明

### 2) 服务脚本化（Lua/Python 等）
- 优点：热更便捷，生态工具丰富
- 缺点：
  - 性能、类型安全、调试体验与 C++ 差距明显
  - GC/解释器开销与不可控抖动
  - 与现有 C++ 资产融合成本不低

以上方案没有绝对“完美”的，核心痛点在于：如何既保留 C++ 性能/工程资产，又让热更安全、可靠、低侵入？

## 我们的思路：基于写时拷贝的“实时存档”动态库

目标：
- 热更前快速生成“强一致快照”，即将服务器内存态序列化到磁盘
- 快照完成后，进程可无损退出/切换，新进程从快照“快速恢复”
- 整个过程对业务代码低侵入，不要求重构为无状态
- 出问题可“回滚”到上一份快照

核心理念：
- 借鉴 Redis 的 RDB 保存机制，利用 CoW 将快照过程从业务线程“隔离”出来
- 在类 Unix 上使用 fork() + CoW，子进程基于父进程瞬时内存视图进行序列化
- 在 Windows 上，由于缺少 fork，我们提供同步快照路径：在受控时机生成一致性视图，保证正确性优先（工程上可根据服务窗口选择）

效果：
- 快照内容是“真实内存态”的只读视图，序列化过程中业务继续写不会污染快照
- 快照格式紧凑（LZF 可选压缩、CRC64 校验），落盘原子写入
- 热更流程变为：先存、再切、再读（从快照恢复）

## 架构与数据流

组件划分：
- background_save（核心库）
  - RDB Writer：序列化/压缩/校验
  - File Manager：临时文件写入 + 原子重命名
- 接入层接口
  - rbs_database_interface_t：由业务实现“如何枚举所有 key/如何取值”
  - rbs_config_t：控制输出文件名、是否压缩、是否校验、是否 fsync
- 平台适配
  - Unix：fork + 后台保存（异步）
  - Windows：受控同步保存（保持一致性）

数据流（热更前触发一次快照）：
1) 业务线程触发保存
2) Unix：fork 子进程；Windows：进入受控保存路径
3) 遍历数据接口，序列化为 RDB
4) 临时文件写入完成后原子重命名，校验通过
5) 通知保存完成，进入热更窗口

## 与现有方案的对比

- 相比“无状态化”
  - 不强制将状态外移，降低改造成本
  - 快照是“本地热备”，网络抖动与一致性复杂度更低
- 相比“共享内存”
  - 更友好的对象模型与演进方式，不强制跨进程共享
  - 底层由文件/序列化支撑，可回放、可审计
- 相比“逻辑插件化”
  - 避开 ABI 雷区；状态通过快照跨版本迁移
  - 新旧版本边界清晰：以快照为交换介质
- 相比“脚本化”
  - 保持 C++ 性能与工程资产，热更成本可控

取舍：
- 首次接入需要实现“枚举/取值接口”（一次性工作）
- Unix/Windows 的实现路径不同：Windows 以一致性优先，吞吐略低
- 快照文件需要磁盘空间与生命周期管理（项目提供轮转/校验）

## 接入指南（C/C++）

核心 API（简化展示）：
- rbs_save_background(&config, &db_interface)：触发保存
- rbs_is_save_in_progress()：查询是否仍在保存
- rbs_get_error_string(code)：错误信息
- rbs_set_default_config(&config)：默认配置

你需要实现数据库接口：
- get_all_keys(keys, count)：枚举所有 key
- get_key_value(key, kv)：根据 key 导出 value
- free_key_value(kv)：释放资源

最小接入步骤：
1) 在你的服务中实现 rbs_database_interface_t 三个回调
2) 在合适时机触发 rbs_save_background（例如热更前的“准备阶段”）
3) 等待保存完成（Unix 通常较快；Windows 根据数据量而定）
4) 将生成的 RDB 文件作为“状态移交”给新版本进程
5) 新进程启动时，从 RDB 文件恢复内存状态（按你的对象模型）

编译与运行基准测试（Windows 示例）：
- 构建：
  - 在项目根运行 `build.bat` 或进入 `build` 目录，编译生成 `test_benchmark.exe`
- 运行：
  - `./test_benchmark.exe`

## 热更剧本（推荐实践）

1) 进入准备态
   - 停止接入新请求或将请求导向其他实例（灰度/滚动）
   - 业务层进入“可保存”窗口，保障枚举接口返回一致集
2) 触发实时存档
   - 调用 `rbs_save_background()`
   - 等待完成（Unix 通常较快；Windows 根据数据量而定）
3) 切换版本
   - 退出旧进程（或下线该实例）
   - 拉起新版本二进制
4) 恢复状态
   - 新版本从快照加载，完成内存重建
   - 健康检查通过后，恢复流量
5) 应急回滚
   - 如发现问题，使用上一份快照回退到旧版本

安全性与一致性保障：
- 临时文件 + 原子重命名，避免中间状态
- CRC64 校验，防止文件腐败
- 可配置 fsync，满足落盘持久化要求

## 性能与测试

项目内置性能基准，部分结果（Windows，同一环境，仅供参考）：
- 10 keys × 1000 次：平均 0.14 ms/次，约 73,799 keys/s，5.17 MB/s
- 100 keys × 100 次：平均 0.29 ms/次，约 349,568 keys/s，95.66 MB/s
- 1000 keys × 10 次：平均 6.17 ms/次，约 162,012 keys/s，168.60 MB/s
- 配置影响：
  - 压缩开销约 +6.7%
  - 校验和开销约 +1.4%

工程建议：
- 对延迟极敏感的场景，可关闭压缩/校验以争取纯速度
- 对数据可靠性敏感的场景，开启 fsync + checksum
- 批量合并小型保存，提高吞吐

## 何时适用、何时不适用

适用：
- 以 C/C++ 为主的高性能服务
- 希望保留现有对象模型，不愿重构成“无状态”
- 热更需要严格的“可回滚”与“强一致快照”能力

不适用：
- 纯无状态服务（已有成熟外部状态体系）
- 需要“细粒度、秒级增量热更新”的极端场景（可与脚本化结合）

## 典型问题答疑

- 会不会卡主线程？
  - Unix 下保存在子进程进行；Windows 提供受控同步保存，建议在“窗口期”执行
- 快照文件多大？
  - 取决于对象总量与开启的压缩策略；项目提供轮转与输出路径配置
- 数据模型变更如何处理？
  - 通过快照做“版本间迁移”，在新版本加载时做兼容转换（推荐定义向后兼容的读入流程）

## 总结

“基于写时拷贝的实时存档动态库”把“热更状态难题”转化为“可审计、可回放、可回滚”的持久化快照问题。借助 Redis 风格 RDB 的工程化实践，我们在 C++ 服务场景下达成了以下目标：
- 最小侵入接入
- 强一致与可回滚
- 跨平台可用（Unix 最佳，Windows 保守但可靠）
- 可量化、可验证的性能表现

如果你正在为 C++ 服务端的热更与状态迁移发愁，这种方案值得尝试：把内存态一次性固化，再以文件为边界安全切换，让热更可控、让回滚真实可用。

如需参考实现与基准测试方法，可直接使用项目提供的接口与测试程序，按需开启压缩、校验、fsync 等选项，基于你的业务数据做进一步的验证与调优。
